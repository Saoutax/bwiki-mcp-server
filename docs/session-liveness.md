# 会话失效处理

## 背景

BWiki 对失效的 cookie 不报错，而是把请求当匿名访客处理，`userinfo.name` 变成调用方的出口 IP：

- 读操作照常返回公开内容，无异常提示；
- 写操作照常成功，但页面署名是 IP 而不是用户。

成功响应里没有任何字段提示身份已变。

## 机制

| 阶段   | 机制                                      | 时机                                   |
| ------ | ----------------------------------------- | -------------------------------------- |
| 启动   | `bwiki/sessionGate.ts` 校验已存会话       | 服务启动时；失败不退出，只记为未登录   |
| 运行中 | `wikiProbe`/`loginGate`/`liveness` 查身份 | 每次 wiki 工具调用前（读操作和写操作） |

判定依据：`userinfo.name` 是否为纯数字 UID（`/^\d{5,}$/`）。BWiki 不使用常规 MediaWiki 账号，`id` 恒为 0、`anon` 不可靠，只有 name 是否为数字可信。

## 行为

| 情况                    | 行为                                                                 |
| ----------------------- | -------------------------------------------------------------------- |
| 会话有效                | 放行                                                                 |
| 无会话 / 会话失效       | 返回 `authentication` 错误并启动登录流程；**不断开连接**，登录后重发 |
| 会话已判定失效          | 后续调用直接进入重新登录流程，不再重复探测                           |
| 传输失败（wiki 不可达） | 返回 `upstream_failure` 错误，连接保持，不计为登出                   |
| 读操作                  | 与写操作一样校验身份，不降级为匿名                                   |
| 任一 wiki 判定失效      | 对全部 wiki 生效（共用一份会话）                                     |
| 登录成功                | 会话文件写入后立即生效，无需重启服务；进程内同时只允许一个登录窗口   |

## 为什么不断开连接

断开 MCP 连接会迫使用户重启客户端或重新建立连接，而登录本身只需要在浏览器里完成。当前设计选择保留连接、返回可解释的 `authentication` 错误，并在后台启动一次登录；用户完成后重发请求即可。

登录门的提示消息会说明当前处于"等待登录"还是"需要先运行 `bwiki-mcp-server login`"（无人值守环境）。`BWIKI_MCP_NO_BROWSER_LOGIN=1` 时不会自动弹浏览器，`bwiki-login` 工具也会提示改用命令行登录。
